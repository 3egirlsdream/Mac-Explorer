# Mac Explorer 启动性能优化方案

日期：2026-11-03  
状态：方案报告，尚未实施或完成启动性能基准测试。

## 1. 目标与结论

在保留现有插件、文件管理、局域网传输、Copilot 和商店功能的前提下，缩短启动到可交互的时间，并减少启动后数秒内的卡顿。

优先采用 **启动分段测量、ReadyToRun 对照实验、首屏初始化调整**。暂不推进全面 Native AOT 迁移，不将裁剪作为本轮前提。ReadyToRun 保留正常 .NET 运行时、JIT 和动态程序集加载能力，适配成本显著低于 Native AOT。

目前没有本项目的对照数据，不承诺具体提速百分比。以下瓶颈是源码检查发现的候选项，需通过测量确认。

## 3. 优化方案与优先级

### P0：建立启动分段测量

先记录以下阶段，使用单调时钟计算耗时：

1. 外部启动器发起进程启动、进入 `Program.Main`。
2. 平台准备、Avalonia 初始化、应用资源加载。
3. 服务配置与首批服务解析。
4. 主窗口和 ViewModel 创建、初始导航。
5. 第一帧完成、首屏数据展示、首次输入响应。
6. 后台服务开始和完成，以及启动后前 5 秒的响应情况。

区分“代码已提交渲染”“窗口已打开”和“用户实际看到完整首屏”，不要仅以 `Show()` 返回或 `Opened` 时间作为启动完成指标。框架内测点无法覆盖进入 Main 之前的运行时和系统加载开销，应配合外部计时及必要的录屏验证。

诊断默认关闭或仅在基准模式启用；记录阶段名称和耗时，不记录路径、文件名、搜索内容或画面。避免同步写盘、强制 GC 等测量行为影响结果。

难度：低到中。收益：提供后续改动的决策和回归依据。

### P1：ReadyToRun 独立对照实验

发布时单独启用：

```xml
<PublishReadyToRun>true</PublishReadyToRun>
```

先通过命令行属性构建实验版本，确认收益后再考虑加入正式发布配置。继续保留现有插件和 JIT，不同时启用 Native AOT、裁剪或单文件发布，以便明确收益来源。

预期作用是减少启动时的即时编译工作，不会消除数据库、磁盘、网络和布局成本。代价是发布耗时和程序集体积增加；更大的加载体积也可能抵消部分收益。

ARM64 和 Intel 分别构建、测量与验收。比较实际 `.app` 和压缩分发包大小，不将单个程序集的体积增长比例直接套用到整个安装包。

难度：低。功能影响：原则上保持原有运行模式，仍需验证插件加载、原生库、签名与更新流程。

### P1：减少首屏前的非必要工作

检查 LocalSend、标签重试、插件初始化的同步前置工作，将不影响首屏正确性的部分安排到首帧后分阶段执行。

- 主题、语言、窗口位置、当前目录必要状态仍在首屏前准备，避免闪烁和错误内容。
- LocalSend 在首屏后尽快启动，记录接收服务的实际就绪时间。
- 插件入口若提前被点击，应等待同一初始化任务，并提供现有风格的状态反馈，不能静默失效或重复初始化。
- 标签重试保留必要的数据一致性和执行顺序，不能只为提速任意延后必需状态。
- 启动后立即退出时，取消尚未开始的工作并正确等待已启动工作结束。

不要将所有操作简单包进 `Task.Run`；UI 和部分原生对象有线程约束，后台并发也会争抢 CPU 与磁盘。

难度：低到中。功能影响：改变部分服务的就绪时序，不删除功能；需要避免初始化竞态。

### P2：延迟解析非首屏服务

重点检查 `RegisterOmniboxProviders` 和主窗口 ViewModel 依赖链。

注册服务通常成本很低，解析服务及运行其构造函数才可能触发读盘、数据库访问和连锁初始化。先测量耗时，再对明显昂贵的依赖使用工厂或惰性访问。

- 搜索框先注册轻量提供器，查询时才解析底层服务。
- 检查 AI、归档、远程操作等服务是否确实需要在首屏实例化。
- 高频功能可在首屏稳定后低优先级预热，避免把所有等待转移到用户第一次点击时。
- 保持现有单例、窗口作用域、事件订阅和释放规则；关闭窗口后不得因预热任务继续持有窗口。

难度：中。功能影响：首次使用可能增加等待，应连同首次搜索、预览和功能打开耗时一起验收。

### P2：控制启动后的后台竞争

在现有索引延迟 2 秒、更新检查延迟 10 秒的基础上，按任务实际成本安排启动顺序与并发，而非继续堆叠固定延迟。

优先级建议：

1. 当前目录加载、可见行图标和输入响应。
2. 常用交互准备、LocalSend 和必要后台服务。
3. 插件扫描及高频功能预热。
4. 非紧急索引、维护及其他批量后台工作。

具体顺序以测量和功能依赖为准。限制昂贵任务并发，支持退出取消，避免无限延后后台服务。应用空闲回调只能作为调度手段，不能当作资源充足或首帧已呈现的保证。

难度：中。主要改善窗口出现后短时间内的卡顿。

### P3：局部编译绑定与首屏资源优化

若测量确认绑定和布局占比明显，再优先迁移主窗口、侧栏、首页的绑定，补齐 `x:DataType` 和编译绑定，不一次性重写全部页面。

同时检查首屏是否重复创建页面、提前解码不可见缩略图，或为背景主题做了不必要的重复合成。项目已有页面懒加载、可见范围缩略图加载和背景缓存机制，优化应基于现有实现，不重复建设。

绑定迁移后验证命令、双向编辑、语言切换、主题切换及动态模板。背景优化保留用户选定效果，不通过降低画质或关闭功能取得表面收益。

难度：中。收益取决于实测占比，优先级低于首屏依赖和初始化调整。

## 4. 验证方法

### 4.1 对照组

在相同源码快照、相同构建环境与相同测试数据下比较：

- A：当前 Release 基线。
- B：仅开启 ReadyToRun。
- C：仅调整首屏初始化。
- D：组合已证明有效的改动。

同批测试交替运行版本，避免将系统缓存、温度或后台负载差异误认为收益。各场景建议至少运行 10 次，报告中位数、范围及异常样本；若要报告 P95，应增加样本量。首次启动与重复启动分开统计，不将新测试目录等同于操作系统文件缓存冷启动。

### 4.2 指标

| 指标 | 验收意图 |
|---|---|
| 发起启动到第一帧 | 窗口是否更快显示 |
| 发起启动到首屏可交互 | 是否真正更早可用，而非提前显示空窗口 |
| 前 5 秒输入响应及长停顿 | 是否避免初始化后续卡顿 |
| 首次搜索、预览、设置及插件操作耗时 | 是否把成本简单转移到第一次使用 |
| LocalSend 就绪时间 | 延后启动是否影响接收体验 |
| 启动阶段峰值与空闲内存 | 是否以明显增加内存换取提速 |
| `.app`、分发包体积及发布时间 | ReadyToRun 的成本是否可接受 |

覆盖首页启动、目录启动、恢复目录、不同文件数量、浅深主题及自定义背景；商店版与网站版分别验收权益和插件相关差异。不存在授权结果时不能默认开放高级功能。

### 4.3 项目测试约束

- 构建使用 `-p:SkipMacOSReleaseDMG=true`。
- 真实应用通过 `bash Tools/Testing/run-isolated.sh <可执行文件> [参数...]` 启动。
- 原生验收启动新构建的 `.app/Contents/MacOS/MacExplorer`，不复用普通实例。
- 测试数据只放在隔离根目录内，不使用真实用户的历史、收藏和目录。
- 首次运行与已有配置场景使用可重复准备的隔离数据，并检查隔离启动器的清理行为。
- 日常业务改动运行 `fast`，共享 UI 变化增加 `ui`，发布或测试基础设施变化运行 `full`；真实进程和网络相关变化补充对应 integration 验证。

现有自动测试通过不等于启动提速；性能结论必须来自同条件对照。测试入口详见 [Tools/Testing/README.md](../Tools/Testing/README.md)。

## 5. 实施顺序与停止条件

1. 固定源码快照，建立计时与基线，确认主要耗时阶段。
2. 单独构建 ReadyToRun 实验版，比较速度、体积和功能。
3. 处理实测最重的首屏同步工作和服务依赖。
4. 评估后台竞争和首次功能使用，再决定是否迁移绑定。
5. 仅将通过回归且收益稳定的改动纳入正式发布。

若某项收益落在测量波动范围内，或造成首屏闪烁、首次操作明显变慢、服务不可用、内存释放退化，应回退该项或继续定位，不为了保留优化而降低验收标准。

# LocalSend：10 秒目标的发现算法与验收（2026-10-22）

> 状态：高强度方案因实机遗漏和系统卡顿反馈未通过验收，已撤回。下文算法部分保留为实验记录，不代表当前启用的实现。

## 目标与边界

目标是降低跨子网冷发现的延迟和遗漏概率，并覆盖不同地址位置；不以提前注入目标 IP、历史设备或特定子网换取结果。单个可路由私有 /16 内，新增低成本全范围 UDP 探测；多接口交错推进。没有地址来源时，不能保证任意 RFC1918 网络、任意掩码、IPv6、休眠手机或被 ACL 隔离的设备在 10 秒内发现。实际完成时间还受操作系统发包背压和对端响应影响。

本轮不修改路由、手机 IP、交换机或手机设置；真实手机验证仍只发生在本机 172.20.202.91/24 到 172.20.205.41 的现有跨子网路由上。其他地址与掩码的验收是候选集合及调度模拟，不冒充更换了真实网络。

## 资料与选择

- [LocalSend 协议](https://github.com/localsend/protocol/blob/main/README.md)：发现公告携带 HTTP 端口，接收端通过 `/register` 回连。
- [官方 1.17 UDP 实现](https://github.com/localsend/localsend/blob/v1.17.0/common/lib/src/task/discovery/multicast_discovery.dart)：接收来自任意地址的数据报并按来源 IP 回连。由此推断可将相同公告用于单播；本轮已在 Xiaomi 手机验证兼容性。单播 UDP 不依赖路由器转发本地组播组。
- [Nmap 时序与性能](https://nmap.org/book/man-performance.html)：有界并行、时序预算、有限重传以及过快扫描可能降低准确性的权衡。
- [ZMap 论文](https://zmap.io/paper.pdf)：借鉴分散目标的置换思想，减少把后续候选长期压在一个连续地址块后面。

当前实现为普通应用层 UDP/TCP，无需原始套接字或管理员权限，也未引入交换节点。

## 已撤回的高强度实验实现

1. 原组播与已验证设备直连保留。增加独立的单播 UDP 公告扫描，接收方回连后仍进行 TLS 指纹核验。
2. 历史、用户配置、本机范围与附近候选优先；随后使用 `index * 40503 + seed mod 65536` 遍历 16 位地址。步长为奇数，模 2^16 时为双射；每个地址恰好一次，多个接口对应的不同 /16 按轮转交错，不按观测手机地址排序。
3. 使用 64 包批次进行时间预算。前 2048 个候选按最多 2048 包/秒启动，给附近设备回包窗口；随后上限 10000 包/秒，同时限制 JSON 载荷带宽为 4 MiB/秒。不积攒延迟期间的额度形成补偿突发。
4. UDP 使用非阻塞 socket，避免一个目的地址的发送等待挡住整个枚举；WouldBlock 仅做一次可取消的短等待重试，缓冲区不足或网络关闭时退让。记录成功发送数、完整轮次数与发送错误数；发送成功本身不代表对端收到或回复。
5. TCP 后备持续补位，上限 64 并发、200 次探测/秒。静默超时仅限速重试一次；明确关闭的端口不重复。TCP 与 HTTPS 验证通过有界队列分开，未知验证最多 2 个，全部 HTTP 仍共享 4 并发上限。
6. 自动发现可以在 HTTPS `/info` 与证书指纹一致后展示设备，双向注册继续在后台进行。健康的已验证信息不会仅因 `/register` 暂时超时被移出在线列表。显式手动连接和内部定向扫描仍要求原有完整注册，相关取消与指纹用例保留。
7. 活跃轮次刷新只唤醒和续扫，不插入重复范围；完整轮次后的刷新合并处理，UDP 轮次至少间隔 10 秒。改网段会取消并排空两个扫描阶段后重建，关闭/网络切换等待全部任务结束。文件传输期间暂停未知地址扫描。
8. 去掉 TCP 后台对所有接口合计只取 65536 个候选的截断，避免多个不同 /16 时尾部范围永远无法推进。多个 /16 的总量更大，不承诺它们合计在 10 秒内完成。

## 真实验收方法

探针源码位于 `/private/tmp/localsend-discovery-20261022/probe/`，只通过参数将目标地址用于设备快照成功判断。每轮经 `Tools/Testing/run-isolated.sh` 创建新目录，使用空的内存设置，启动时输出 `SCAN_SUBNET='' HISTORY_PRESENT=False`。不覆盖系统网卡或候选生成，不调用手动连接来完成自动发现，不发送文件。TCP 监听随机端口，实际端口随公告发给手机。

计时从 `StartAsync` 前开始，包含新测试身份初始化、服务启动、核验与 200ms 快照通知。TCP 后备组仅把 UDP 发送替换为 no-op，仍运行相同候选与真实 TCP/TLS。用户确认手机亮屏并保持 LocalSend 前台后进行最终多轮验收。

共享工作区有其他构建发生 PDB/引用程序集争用；验收改在 `/private/tmp/localsend-under10-source/` 的独立源码快照构建，已逐文件核对本轮 LocalSend 实现与测试和原工作区一致。其余聊天的改动保留在原工作区。

## 中间失败与处理

- 单纯提高并发和立即高速发送的版本出现真实手机遗漏；保留 `under10-phone-1.log`（100 秒未发现）、`diagnostic-run.log`、`phone-tls-split-1.log` 等日志，不计作通过。
- 现场曾出现 `/info` 直连正常而完整注册超时，促成在线核验与双向注册分离；更长时间的诊断中 GET 也出现过超时，不能把所有遗漏归因于注册或手机后台。
- 首轮前台 TCP 后备三轮中两轮约 4.9 秒、另一轮 15 秒未发现，促成一次限速超时重试。
- 旧的逐地址 await UDP 发送实测 15 秒仅完成约 31000 次发送，未完成 /16；因此改为非阻塞发送。模拟的全覆盖结果不等于真实网络全覆盖。
- 原始日志保留在 `/private/tmp/localsend-discovery-20261022/`，临时目录可能被系统清理。

## 最终结果

本轮高强度方案未通过验收，已撤回全 /16 UDP 单播扫描及对应模拟速度测试，恢复 TCP 上限为 16 并发、64 次探测/秒。保留连续扫描队列、HTTP 验证分离、刷新不重扫、有限超时重试与 TLS 信息核验等优化。未继续实网扫描。

最后一版真实手机三轮分别为 9.324 秒、15 秒未发现、12.726 秒；关闭真实 UDP 发送后的 TCP 组为 10.464、8.263、7.806 秒。另一次真实广域发送试验在 15 秒内仅发送 37257 个 UDP 公告且未发现手机。不能据模拟全覆盖约 7.7 秒的结果声称真实网络在 10 秒内可靠发现。

撤回前回归结果为 fast 894 通过、2 跳过，LocalSend 集成 55/55 通过。这些结果证明功能用例通过，不证明系统负载或实网发现速度合格。

## 系统卡顿排查与止损

用户报告扫描测试期间鼠标不能移动，随即停止继续验收；检查时本轮 DiscoveryProbe 和测试进程已退出。没有卡住当时的 CPU、线程栈、WindowServer 或内核采样，无法把某个子系统确认为唯一原因。

高强度方案同时运行最高 10000 包/秒的 UDP /16 遍历和 64 并发、200 次/秒的 TCP 探测，早期还试过更高 TCP 并发。后台 Task.Run、异步网络 API 和并发上限已经存在；缺少线程不是当前证据支持的解释。高速逐地址系统调用、套接字建立/取消、网络协议栈及网关负担可能造成反压；非阻塞 SendTo 也不代表调用没有 CPU 和内核成本。增加线程并不能解除这些资源约束。

2026-10-22 14:06 左右的退出后快照：物理内存 32GiB，使用约 31GiB，压缩约 15GiB；swap 使用约 9.3GiB；负载均值约 15.9，CPU 约 57.6% user、14.6% sys、27.7% idle，且有其他编辑器、模拟器与构建任务。采样窗口 swap 增量为 0；不能用累计 swap 占用证明当时正在抖动，也不能把其他进程视为本轮扫描创建。该快照支持机器余量有限，不能重建卡顿瞬间因果。

安全调整移除了高速 UDP 全范围遍历，而不是仅增加线程或仅缩小批次。当前运行的普通应用 PID 76878 在 09:15 已启动，早于本轮高强度实验；代码修改不会热替换进程内的程序集。后续若进行实网验收，应串行运行、限制发包并记录系统与进程负载、UI 响应，发现反压就降低强度；不再以高发包率换取未经证实的 10 秒承诺。

撤回后在独立源码快照使用单节点、禁用节点复用的构建成功。fast 回归 884 通过、2 跳过、0 失败（13.74 秒）；另行串行执行 8 个 LocalSend 关键回归全部通过（18.924 秒），覆盖扫描持续推进、慢注册不阻塞、刷新不重复、网段重建、有限重试、速率/并发上限及停止排空。后者使用 TCP 测试替身或回环地址，不重新执行真实手机或 /16 扫描。速率用例首秒实测 64 次、最大 TCP 并发 16。没有新的桌面卡顿采样或实网性能验收，不能据此宣称卡顿已完全解决或 10 秒达标。

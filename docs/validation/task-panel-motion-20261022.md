# 任务面板文案与开合优化（2026-10-22）

## 验收状态修正

功能回归通过，性能验收尚未完成。用户反馈原生基准运行时整机卡顿、鼠标瞬间无响应；原始样本也有 1.7 秒以上的回调停顿。此前根据 p95 改善汇报完成过早，不能将长停顿直接归因为系统调度抖动。目前没有同期线程／GPU／WindowServer 跟踪，尚不能确定整机停顿的根因；不继续自动重跑压力负载。

用户进一步确认卡顿时光标本身也完全停住，因此不能仅按应用内点击无响应处理。只读检查时已无 FastListBench 进程，当前内存可用比例约 55%；这些当前状态不能证明卡顿发生时的资源状态。找到的 WindowServer CPU 报告来自 10 月 20 日，不属于本次基准，不能作为本次根因证据。基准降载与停止阈值已通过单独构建检查，没有再次执行原生压力负载。

基准现已将默认负载降为 2 项、50ms 进度通知、3 次开合，原 100 项／8ms 负载需显式 `--tasks-stress`；单次开合超过 500ms 后停止后续轮次。下面保留原始压力数据供调查，不作为流畅度验收通过的依据。

“传输任务”统一改为“任务”，同步简体、繁体、英文与法语，面板和独立任务窗口共用现有本地化 key。

开合由 UI 线程的 `Task.Delay(16)` 循环改为合成线程的 `CompositionVisual.Translation` 关键帧动画，保持 220ms 和三次缓出。先设置动画结束后的基础坐标，避免重复开合后残留屏外位置。任务通知按 50ms 合并；隐藏时不刷新列表，动画期间保留行控件，结束后同步最新状态。首次创建 Presenter 不再额外刷新一次，面板排除侧栏玻璃背景采样。

## 原生基准

使用 `FastListBench --tasks-only` 和 `run-isolated.sh`；每组先预热，再开合 5 次，持续进度来自每 8ms 的合成更新，不是真实文件传输。改后独立重跑两次。完整数据见 [task-panel-motion-20261022.json](task-panel-motion-20261022.json)。

| 任务数／进度更新 | 改前 p95 | 改后 p95（两次） | 布局次数：改前 → 改后 |
| --- | ---: | ---: | ---: |
| 2／无 | 15.9ms | 16.6／16.7ms | 5 → 5／5 |
| 2／每 8ms | 15.4ms | 16.7／16.8ms | 268 → 10／10 |
| 100／无 | 13.6ms | 17.6／16.9ms | 5 → 5／5 |
| 100／每 8ms | 116.9ms | 16.8／41.1ms | 160 → 10／9 |

所有改后场景的 UI 线程坐标修改次数均为 0，改前为 83–127 次。表中 p95 是 `RequestAnimationFrame` 的 UI 回调间隔，并非 GPU 或显示器呈现 FPS。100 项持续更新场景最大回调间隔为 689／1731ms，长停顿原因尚未定位，不能据此宣称全程稳定 60 FPS。合成动画本身不再依赖这些 UI 回调逐帧推进。CPU 总耗时存在波动，不以本次样本宣称整体 CPU 降幅。
